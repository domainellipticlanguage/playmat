## 1. Card context menu was dead (real bug)

Clicking Tap / Turn face down / etc. on a battlefield card did nothing.

Not a wiring problem — `menuItemsFor()` already matches crucible's
`MtgCardMenuItem` shape (`{label, action}`). The cause:

- The crucible menu renders via `createPortal(..., document.body)`, but **React
  portals bubble through the React tree, not the DOM tree**, so its `pointerdown`
  reached `Battlefield.onPointerDown`.
- The menu calls `stopPropagation` on `mousedown`, not `pointerdown`.
- In that handler `e.target.closest('[data-guid]')` is null (the menu node is
  outside the card's DOM), so it fell through to the marquee branch and called
  `setPointerCapture` on the viewport.
- Capture redirects `pointerup` to the viewport, so the browser never fires
  `click` on the menu item. The action never ran.

Fix: `Battlefield.onPointerDown` bails on `.mtg-card-menu, .ctx-menu`.

**Worth a browser check** — this is the one fix whose mechanism I inferred from
reading rather than observing. If menu items are still dead, the next suspect is
the document-level `mousedown` close handler in `MtgCard.js` unmounting the item
before its `click` lands; that would need a different fix (mousedown-to-activate,
or our own menu instead of crucible's).

## 2. Hand drifted off screen

`.hand-strip` was pinned `left: 600px; right: 300px` — only 540px of strip on a
1440px laptop, so a normal 7-card hand overflowed and `.table-main
{ overflow: hidden }` clipped both ends.

- Bounds are now viewport-relative (`clamp(96px, 34vw, 600px)` / `clamp(8px,
  17vw, 300px)`). Lower bound 96px is chosen so the strip still clears the
  ~470px bottom-left HUD at 1440px+.
- `Hand.tsx` measures the strip with a `ResizeObserver` and solves per-card
  overlap (`--hand-overlap`) so the fan always fits, floored at `-46px` so cards
  stay grabbable.

Unchanged by design: `.hand-card { transform: translateY(34px) }` still tucks the
bottom of each card below the viewport edge — that's the existing peek-up-on-hover
design, not the bug that was reported.

## 3. Root always lands in the lobby; room code always in the URL

- `App.tsx` auto-rejoin now requires `?room=` naming your saved session. A bare
  root is always the lobby — previously a saved `lastSession` dragged you back to
  the old table with no way out short of clearing localStorage.
- One effect in `App.tsx` writes the code to the URL whenever a session exists.
  Removed `Lobby.tsx`'s duplicate `replaceState` — single source of truth.
- An un-joined `?room=` is left alone so invite links still prefill the lobby.
  `Table.tsx`'s Leave button still clears it.

## 4. Card ownership is now enforced (data-model change)

**Rule: a card only ever occupies its own owner's library / hand / graveyard /
exile / command zone.** Battlefield is the sole exception — `controllerId` still
lets you take control of an opponent's permanent.

This **inverts the old Z-6** ("any card can be moved to any zone of any player").

- `MoveTarget.zoneOwnerId` is **gone**. `moveCard` resolves the destination owner
  from the card's own `ownerId` via the new `ownerOf()`. It is not overridable.
- New `canPlaceIn(guid, zone, zoneOwnerId)` gates the drop sites (Hand,
  Battlefield, PlayerHud piles) so dropping on another player's pile is
  **refused** (card snaps back) rather than silently rerouted home.
- Defense in depth: even if a call site forgets the gate, `moveCard` cannot
  produce a cross-player placement.

## 5. Teaching mode — others may act on your hand

- `showHandToTable` was a local-only pref, so peers couldn't know. It now ships
  on `PlayerState` and `setShowHandToTable` publishes a player event (previously
  only card reveals, so an empty hand announced nothing).
- Revealed hand cards in another player's HUD get a right-click menu (play /
  discard / exile / tuck) gated on `canActOnHand = !isMe && state.showHandToTable`.
  Every action routes into the **owner's** zones automatically via rule 4.

### The subtle part — read before touching `store.applyStateEvent`

Only your own actions call `removeFromHidden`/`addToHidden`, so anything a peer
does to your hidden zones must be folded in by the store. There are **three**
cases, and they are deliberately handled as one remove-then-insert:

| case | example |
|---|---|
| in | peer mills you / tucks a card into your library |
| out | peer discards from your hand (teaching mode) |
| **both** | peer moves your hand card onto your library |

My first attempt used two independent blocks (the original fold-in, plus a new
removal block). That **duplicates the card** on the both-case: the insert bails
because the guid is still in `hand`. Covered by
`store.test.ts` → *"a peer tucking my hand card lands it in my library exactly
once"*. Don't split it back apart.

Counts self-heal: `connection.ts` notices `handCount`/`libraryCount` drift after
a remote hidden change and calls `actions.publishMyCounts()`.

## 6. Dragged battlefield cards ride above the player HUDs

Requested behaviour: lifted while dragging; falling back underneath on drop is
fine.

Naive fix (raise `.battlefield-viewport` z-index) **breaks drop detection** —
`elementFromPoint` would return the table surface instead of the pile. Instead,
locally-dragged cards are portaled into a `.drag-layer`
(`position: fixed; pointer-events: none; z-index: 60`) that re-uses the *identical*
world transform string, so the card doesn't shift a pixel crossing layers. Remote
drag ghosts stay in the world.

Side effect: `TableCard` unmounts/remounts on drag start/end. Harmless today
(crucible's internal `rotationIndex` is unused — we drive rotation by prop), but
watch for image flicker.

**Worth a browser check.**

## 7. Library contents are now published (data-model change, user-chosen)

Nathan chose this explicitly over two alternatives (owner-executed remote
commands; leaving it hidden with better UI). Each player's library order ships on
`PlayerState.library` (~3.9 KB for a 99-card deck — fine for AppSync Events and
DDB item limits).

- Any player can click a library to browse/search it, drag its top card out, or
  mill it — the same reach as a graveyard.
- `SearchModal` takes an optional `ownerId`; `ModalState` is now
  `{ kind: 'search'; ownerId?: string }`.
- Taking a card to the battlefield lands it on the **owner's** seat, since the
  owner still controls it.

**Reordering stayed owner-only** (new Z-7). Only the owner's client holds the
authoritative array, so a shuffle published by a peer would be overwritten by the
owner's next publish. Searching someone else's library tells you to ask them to
shuffle.

**Accepted cost, stated in §7.3:** every client now holds every deck's exact
order, so a player who goes looking can see their own next draw. The hand is
still private (count only, plus explicit reveals).

## Loose ends / suggested next steps

1. **Browser pass on items 1, 2, 6** — none were visually verified.
2. **Root `npm run build` is broken, and was before this work.** It runs
   `npm run build -w shared`, but `shared/package.json` has no `build` script
   (it's consumed as raw TS via `main: src/index.ts`). Use `npm run build -w web`.
   Worth fixing properly.
3. **Stale browse window.** When you pull a card from a peer's library, their
   client removes it and republishes; until that lands your open modal still
   lists it. Self-corrects, but a spinner or optimistic filter would be nicer.
4. **Control-stealing isn't implemented.** A card taken from a peer's library to
   the battlefield keeps `controllerId = owner`. Real Bribery would set the
   controller to the caster. Out of scope for this batch; the ownership rule
   (item 4) deliberately leaves `controllerId` as the battlefield escape hatch,
   so this is the natural place to build it.
5. **`theirPlayerState()` default lacks `library`.** If you patch a peer's state
   before they've ever published (e.g. adjust life at t=0), you write a
   `PlayerState` without `library`. Harmless — it's optional and the owner's next
   publish restores it — but it's a sharp edge.
6. **Teaching-mode hand is right-click only.** No drag-from-peer's-hand. Would be
   a natural follow-up for parity with your own hand.
7. Vite warns that `actions.ts`/`uiStore.ts` are both statically and dynamically
   imported. Pre-existing; this session added one more dynamic import in
   `connection.ts` following the file's existing pattern.
